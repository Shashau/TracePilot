# TracePilot — Automated REST API Testing & Anomaly Diagnosis

A complete Python hackathon project for problem statement **JP-009**. Configure REST API tests, execute repeated requests, validate contracts, detect anomalies, inspect evidence-based recommendations, and compare a faulty implementation with a repaired implementation.

## Project manual

Open **docs/PROJECT_MANUAL.pdf** for the 14-page Windows setup and project operation manual. An editable Markdown copy is included as **docs/PROJECT_MANUAL.md**. It covers installation, demo steps, live REST APIs, imports, reports, reproducibility, troubleshooting, and presentation.

## Start on Windows

1. Install **Python 3.12, 64-bit (x64)** from [python.org](https://www.python.org/downloads/windows/). Select **Add Python to PATH** and the Python launcher during installation.
2. **Extract the entire ZIP** to a writable folder, such as `Documents\TracePilot`. Do not launch from inside the ZIP.
3. Double-click **START_WINDOWS.bat**. It creates a Windows virtual environment and installs the exact packages from the included `vendor/windows-py312` folder. Internet is not required for this setup once Python is installed.
4. The dashboard opens at **http://127.0.0.1:8000**. Keep the terminal window open.
5. Double-click **VERIFY_WINDOWS.bat** to verify both seeded outputs against the reference files. Double-click **TEST_WINDOWS.bat** to run the automated tests.

The Windows offline bundle targets **Windows x64 + CPython 3.12**. It does not contain the Python interpreter. Do not copy a Mac virtual environment to Windows. The launcher creates the correct environment on each machine from the same pinned versions.

## Start on macOS / Linux

Install Python 3.12 (recommended; 3.11–3.13 supported), extract the archive, open a terminal in the project folder, and run:

```bash
bash start_mac_linux.sh
```

First setup needs internet on macOS/Linux; subsequent launches run locally. The package versions are the same as Windows. The archive contains Windows wheels only; native binaries differ by operating system.

## The three-minute demo

1. Leave **Commerce API**, **seed 42**, and the original suite unchanged.
2. Click **Learn baseline**. The repaired implementation produces **220 requests / 11 passing cases**, with at least 20 samples per case.
3. Select **Demo · faults enabled** and click **Run tests**. Expect **55 requests, 3 passing and 8 failing cases**. With the baseline present, search also receives a local ML latency finding.
4. Inspect **Protect admin report**: an unauthenticated request received HTTP 200 instead of 401. Inspect the evidence and recommended action.
5. Inspect **Reject negative quantity**, **User response contract**, and **Search latency budget**.
6. Select **Demo · repaired**, run again, and get **11/11 passing cases**.
7. Open **Run history → Compare two runs**. Select the faulty run as Before and the repaired run as After. Expect **8 resolved, 0 regressed**.
8. Export an **HTML report** or **Reproducible JSON**.

The repaired mode uses actual alternative handlers supplied in `app/demo.py`; it does not automatically patch another API.

## What is reproducible?

| Item | Same seed + unchanged suite |
|---|---|
| Built-in response bodies and HTTP status codes | Identical |
| Injected faults and deterministic contract findings | Identical |
| Seeded service times and contract pass rate | Identical |
| Canonical reproducible JSON export | Byte-for-byte identical; verified against included golden reports |
| Local ML behavior | Fixed random seed, one model thread, pinned packages; advisory and omitted from the byte-level contract |
| UUIDs, timestamps, history counts, actual wall-clock timings | Intentionally variable; retained in full reports |
| Real external API responses and network timings | Depend on the real service and computer; not guaranteed identical |

The demo sends actual HTTPX/ASGI requests to a FastAPI sample app and performs real response validation. Its **service timing input is a seeded simulation** generated by the sample service and used for repeatable performance-budget checks. The measured elapsed time is stored separately for every sample. **Live HTTP mode always uses measured elapsed time** and never trusts demo timing headers.

## Test your own API

1. Copy `config.env.example` to `config.env`.
2. Set the exact origin you are authorized to test. Example for a local service:

```dotenv
TRACEPILOT_ALLOWED_ORIGINS=http://127.0.0.1:9000
```

3. Restart TracePilot. Use **Configure suite → New suite template**, set `base_url` to `http://127.0.0.1:9000`, and configure the requests.
4. Click **Run tests**. Imported collections remain editable drafts until you save and run them.

Origins include scheme, hostname, and port. A base path such as `/v1` can be included in the suite URL. Redirects are not followed. Credential headers must refer to named `TRACEPILOT_SECRET_` environment variables via `header_env`; raw authorization headers are rejected.

An optional separate sample service can run on port 9000:

```bash
# Windows: use .venv\Scripts\python in place of .venv/bin/python
.venv/bin/python -m uvicorn app.demo:demo_app --host 127.0.0.1 --port 9000
```

Use `examples/live-local-suite.json` as a live-mode suite. This exercises actual loopback HTTP sockets, including real network/processing elapsed timings.

## Configurable test example

```json
{
  "id": "my-api",
  "name": "My authorized API",
  "base_url": "http://127.0.0.1:9000",
  "cases": [{
    "id": "quantity-validation",
    "name": "Reject negative quantity",
    "method": "POST",
    "path": "/orders",
    "body": {"product_id": 1, "quantity": -2},
    "expected_status": [422],
    "negative_test": true,
    "response_type": "json",
    "max_ms": 500,
    "timeout_ms": 3000,
    "repeats": 1
  }]
}
```

Advanced fields: `query`, `headers`, `header_env`, `response_schema`, `assertions`, `expected_headers`, `consistency_paths`, `enabled`. Assertions use JSON Pointers (`/items/0/id`) and `eq`, `ne`, `exists`, `contains`, `gte`, `lte`. Select only stable fields for consistency checks. Repeated state-changing requests may create/update/delete multiple records; use an isolated test environment and configure repetitions intentionally.

## Command-line and CI use

From the extracted project, using its `.venv` Python:

```bash
python -m scripts.verify_demo
python -m pytest -q
python -m scripts.run_suite --mode fixed --output artifacts/fixed
python -m scripts.run_suite --mode broken --output artifacts/broken
python -m scripts.run_suite --suite examples/live-local-suite.json
```

`run_suite` exits **0** for passed contracts, **1** for failed contracts, **2** for setup errors. HTML, JSON, canonical JSON, CSV, and JUnit XML are written to the selected output folder. Use `--baseline --mode fixed` to collect a healthy baseline. `.github/workflows/ci.yml` supplies a Windows/Linux Python 3.12 matrix; it runs when you place this project in your own GitHub repository.

## Troubleshooting

- **Port 8000 is in use:** run `START_WINDOWS.bat --port 8010`, or `bash start_mac_linux.sh --port 8010`.
- **Python not found:** install Python 3.12 x64 and reopen the launcher.
- **Installation fails on Windows:** confirm Python is x64, the complete archive was extracted, and `vendor/windows-py312` is present.
- **Browser did not open:** visit the dashboard URL shown in the terminal.
- **Baseline not ready:** click Learn baseline. Changing a target, seed, contract, or credential invalidates its previous baseline.
- **Target not authorized:** edit `config.env`, then restart. The URL must match the authorized origin exactly.
- **A previous run was interrupted:** start a new run. Completed history remains in SQLite.
- **Reset to the original suite:** import `examples/demo-suite.json`, or stop the server, rename `data/tracepilot.sqlite3` and any `-wal` / `-shm` sidecars as a backup, and restart. Verification uses temporary databases and does not change your dashboard data.

## Practical boundaries

This is a local, single-user hackathon application. It binds to loopback and is not a multi-user hosted product. Concurrency is capped at three cases and repetitions at 30 per case; it is not a load-testing platform. XML validation covers parsing and Content-Type, not XSD. OpenAPI/Postman import is an explicitly documented subset; scripts, OAuth flows, multipart bodies, external references, and inferred negative tests are not imported. Recommendations identify plausible next steps, not a proven server-side root cause. Review evidence and confirm a proposed fix. No competition outcome is guaranteed.

Implementation and validation notes are in `docs/VALIDATION.md`. Dependency source/license notices are in `THIRD_PARTY_NOTICES.md`.
